# Meridian works offline, and tells the owner through whatever channels they set up

Builds on ADR 0006 (trips sync), 0009 (session, gate) and 0010 (itineraries).

**One call raises a Notice.** `notify({ kind, title, body, url, dedupeKey })` in `server/lib/notifier.ts` writes a Notice to a log (`notices.json` in the document store, newest 500 kept) and only then tries each delivery channel. The log is the in-app inbox, so an alert is visible with no channel configured and when every channel is down. The same `dedupeKey` is the same Notice: the insert-if-absent runs inside the store's serialized update, so a retry, a second process on Postgres or a re-run of the daily job cannot send twice. Channels are tried concurrently, each under a 10 second timeout; one failing never stops another, `notify` does not throw for them, and each outcome is saved on the Notice and shown in the inbox. Delivery is at most once: a channel that failed is not retried, because a late duplicate of a price alert is worse than a missed push when the inbox has it anyway. `notify` throws only for invalid input or a failing store.

**Channels**, each optional and switched on by its own variables, read per call: webhook (`ALERT_WEBHOOK_URL`, the old behaviour, now with `kind`, `title`, `body`, `url` beside `text`), ntfy, Telegram, email (Resend's HTTP API, or SMTP spoken directly in `server/lib/notify/smtp.ts`), and Web Push. Web Push is implemented without a library (RFC 8291 encryption and RFC 8292 VAPID, checked against the RFC's own test vector); subscriptions are stored in the document store, and a 404 or 410 from the push service removes the subscription. No dependency was added. Channel status never carries a secret. Telegram errors are rewritten because a failed `fetch` can quote the URL, which holds the bot token. The VAPID subject (a `mailto:` or https URL you choose) is sent to push services, which is what the standard asks for; use an address you are happy to expose to them. With email, Telegram, ntfy or the webhook set up, the title and body of an alert leave the server for a third party the owner picked; nothing else does.

**Daily jobs.** `registerDailyJob({ name, run })` in `server/lib/dailyJobs.ts` is the one hook for work that happens once a day. The watch run is the first user; book-by reminders and re-planning checks should register the same way. A run claims the UTC day in `daily-jobs.json` inside a serialized update, so whoever asks first wins. A job that throws is recorded and does not stop the others. There are two callers. A long-running Node server starts an in-process scheduler from `server/index.ts`: it wakes every 5 minutes, runs once after `DAILY_JOBS_AT` (default 06:17 UTC, the Vercel cron's time), catches up after a restart or a sleeping instance, and `DAILY_JOBS=off` disables it. An external cron can call `GET /api/jobs/daily`. On Vercel the scheduler refuses to start (`VERCEL` is set) and the Vercel cron calls the route, so a day is not run twice; the claim is the second guard. `CRON_SECRET` opens `GET /api/jobs/daily` as well as `GET /api/watches/run`, and nothing else. The claim is taken before the jobs run, so a crash mid-run skips that day instead of repeating it; `?force=1` re-runs one.

**Offline.** The app ships a web manifest, generated icons (an orange meridian mark) and a hand-written service worker (`src/sw/sw.ts`, bundled to `/sw.js` by `scripts/vite-plugin-sw.ts`, no plugin dependency). The worker precaches the built app (JS, CSS, fonts, icons, map glyphs, the RTL text plugin), keeps public API answers (cities, seasonality, livability, news, overlays) network first with a saved copy as the fallback, and keeps the map's country outlines on first use in a bounded cache. The basemap has no tile server, so there are no tiles to cache; if one is added, any `z/x/y` or `.pbf` URL is already routed to the same bounded cache. The web fonts (DM Sans, Instrument Serif, JetBrains Mono, all OFL) are bundled from `src/styles/fonts`, the Google Fonts links are gone, and the Content-Security-Policy no longer lists `fonts.googleapis.com` or `fonts.gstatic.com`.

**Personal data offline.** The worker keeps the owner's GETs (journal, bookings, watches, notices, imports, shortlist) in a separate cache that is only a fallback for a failed request. It is emptied when the page signs out or locks and whenever a personal route answers 401, and it never stores a non-200. Sign-in state (`/api/auth`) and share and calendar links (`/api/shared`) are never stored. Trips are not in the worker's cache at all: they already live in the browser and merge three ways against the server (ADR 0006), and an old server snapshot served as current would make that merge undo recent edits. So offline, trips and itineraries show what this browser last held, and edits to them are kept on this device and sync when the connection returns (the `online` event now triggers a sync). Every other write needs a connection and says "Couldn't reach the server". The offline pill appears only after the browser reports offline or an API request actually fails. A new version waits behind a "Reload" prompt rather than swapping under an open tab; the first install takes over at once.

**What this does not do.** Trips keep their copy in the browser after sign-out, as before: the trip list was never server-gated on the client, and that is a separate decision from the worker's cache. A device that has never loaded the app online has nothing to show. Push needs the installed app on iOS and HTTPS everywhere.

**Phone pass.** At 390 and 360 px every screen already fit without sideways scroll. What was out of reach was small: 24 to 28 px buttons, segmented controls, inline links, and 12 px text fields that iOS zooms into. `src/shell/phone.css` raises them on touch screens and below 640 px and changes nothing for a mouse.

Rejected: `vite-plugin-pwa`/Workbox (a build dependency for a short routing table, and the routing for private data is the part that must be exact and tested); caching trips in the worker (see above); a background-sync queue for other writes (the trip store is already local-first, and replaying a queued write could overwrite a newer edit); retrying failed channels (duplicates); a `web-push` or `nodemailer` dependency (the protocols are small and fixed, and the tests pin them); one channel per deployment (an alert should reach every way the owner set up).
