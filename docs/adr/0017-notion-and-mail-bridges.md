# Notion and Gmail are read-only bridges that land in places the owner already reviews

Builds on ADR 0011 (Personal Windows and the Rotation) and the import queue of the journal (ADR 0004).

The owner plans in Notion and books by mail. Two bridges bring that in without a new store or a new review step: Notion feeds the Rotation's Personal Windows and a pool of candidate places; Gmail feeds the existing Inbox. Neither writes anything the owner has not been shown, neither moves money, and neither keeps content it does not need.

**Notion** (`server/lib/notion/`, `/api/notion`, owner only). A Notion REST client (version 2022-06-28, no SDK) with `NOTION_TOKEN`, an internal integration token that the owner shares the databases with. The token is read from the environment on each call; it is never stored or returned, and status only says whether one is set. Page content never appears in an error: a failed call reports the HTTP status and Notion's error code.

*What it reads.* Two sources, because the owner's workspace does not hold them the same way. **Travel Seasons** is a database with one row per window: a title, a place (a select), a season (peak, shoulder or avoid by keyword: "Peak - Dry", "Avoid - Wet / Extreme"), a start and an end date, and notes. Only the months of the dates are used, so the year does not matter; a range of nearly a year or more is the whole year, and a range that wraps the new year (Nov to Feb) is a wrapping month span, as in ADR 0007. Each row becomes a Personal Window with `source = { kind: "notion", ref: <page id> }` and the notes as its reason. **Location Research** is a page, not a database: a score table (one row per place, a column per dimension and an overall score) and a paragraph per place with an italic line of facts, including a monthly cost range with a stated currency. The importer reads it from the page's blocks, or from an uploaded Markdown export, with the same parser; a database with that shape is read through the property mapping. A place becomes a pool entry: its notes, its monthly budget range as written (amount and currency, never converted), stay range and type where the source has them, and the owner's own scores by dimension. The pool lives in `notion.json` and is exposed as `candidatePool()`; the solver hook of ADR 0011 can read it. Nothing about a place is invented: a field the source does not hold stays empty, and the "Best:" and "Avoid:" months in the prose stay in the notes rather than becoming windows, since Travel Seasons is where the owner records those.

*Mapping.* Property names are a mapping with defaults that match the owner's schema, editable in Settings, so a renamed column is a settings change, not a code change. Database ids come from `NOTION_SEASONS_DB`, `NOTION_RESEARCH_DB` and `NOTION_RESEARCH_PAGE` and can be overridden in Settings (a pasted URL is normalised to its id).

*Matching.* Places are matched to Meridian's cities by exact, accent- and case-insensitive name, narrowed by country when the source gives one, and only when no similarly sized city shares the name (the rule the Inbox uses). Anything else goes to a review list, never a guess: a label that names several places or an area ("Da Nang / Hoi An"), a name with no city, an ambiguous name. Each review item offers suggestions and a city search; the answer, or "ignore this name", is stored as an alias on the label and applies to every later import. A label can map to several cities, and then each gets the windows. Rows with an unknown season or unusable dates are listed too, with the reason.

*Idempotent, previewed, then applied.* A window's id is the Notion page id, and `mergeImportedWindows` replaces the Notion-sourced windows of a place and keeps hand-written ones, so a re-import updates and never duplicates; a row deleted in Notion removes its window. `POST /preview` returns the diff (windows added, changed and removed per place, pool entries, review items) and a digest of everything apply would do; `POST /apply` recomputes it, refuses with 409 if the digest no longer matches (Notion changed after the preview), then writes through the Rotation's place API. An import that covers one database leaves the other's stored data and review items alone. A CSV export of Travel Seasons, and a CSV or Markdown export of Location Research, can be uploaded instead of using a token; CSV rows have no page id, so their ref is a slug of the row title, which is why switching a place between an upload and the API shows as a remove and an add rather than a duplicate.

*Write-back* of the active rotation to a Notion database is off unless both `NOTION_WRITE_BACK=1` is set on the server and the Settings switch is on. It creates one page per committed stay with Name, Dates, Status and Place, remembers the page id and the stay's `updatedAt`, updates only changed stays, and never deletes. It sends the owner's own plan to the owner's own workspace and nothing else.

**Gmail** (`server/lib/gmail/`, `/api/gmail`, owner only). Settings › Inbox connects a Google account with the OAuth authorization code flow and PKCE (S256), scope `gmail.readonly` only, `access_type=offline`, with `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from the environment. The PKCE verifier and a random `state` are kept on the server for ten minutes and spent on first use, so a callback that this server did not start is refused, and the verifier never reaches the browser. The redirect URI is `GOOGLE_REDIRECT_URI` or this request's origin plus `/api/gmail/callback`, shown in Settings so it can be registered. The refresh token is sealed with AES-256-GCM (`v1.<iv>.<tag>.<ciphertext>`) under a key derived from `GMAIL_TOKEN_KEY` (at least 32 characters), so a copy of the document store alone does not open the mailbox. If the key changes or Google revokes the grant, the sync says to disconnect and connect again. Disconnecting forgets the token locally first, then asks Google to revoke it; items already in the Inbox stay.

*Sync.* The queries are the stored prompt's (`docs/ingest/gmail-import-task.md`), minus promotions. The first passes backfill year by year from three years back (`GMAIL_BACKFILL_FROM_YEAR` or a year given to the sync), at most 120 messages a pass, resuming from a saved cursor, so a big mailbox finishes over a few daily runs without one request running long. When the backfill completes, the history id taken when it started becomes the cursor, and each later pass asks Gmail's history for messages added since, intersected with the queries over the days since the last sync; no new mail means no searching and no fetching. If Google no longer has that history, the pass falls back to the queries over a recent window. Each message is fetched as raw RFC 822 into memory and run through the same parser as an uploaded `.eml` (`parseEmailUpload`: schema.org JSON-LD reservations); the candidates are retagged `source: "gmail"` with the Gmail message id and position as `sourceRef`, and go through `addAll`, so the import dedupe (by reference and by content) applies unchanged and a repeat is counted, not added. A message with no reservation markup is counted and dropped: there is no model in this path, which is the price of reading nothing but structured data. **Only extracted fields are stored**: the store holds the encrypted token, the account's address as Google reports it, a history id, a progress cursor, up to 5,000 message ids already seen, and counts. No body, subject, sender or header is written anywhere; a test pins that.

*Future bookings.* A pending stay or transport candidate dated today or later is a plan, not a memory, so the Inbox offers it besides "accept into the journal": a stay goes onto the stop in that city of a trip planned for that year (when the stop has no stay yet) or into a new trip, and a flight, train, bus, ferry or drive is recorded as the booking on the leg that really runs from the booking's departure city to its arrival city (ADR 0010). Trips live in the browser, so this happens there, through the store actions the trip editor uses; applying it clears the item from the Inbox, and the discarded record keeps the dedupe. Lodging mail carries no booking reference in the parser, so a stay added this way has none.

*Without credentials* Settings says exactly which variables to set and what to register; nothing else changes, and the `.eml`/`.mbox` upload in the Inbox keeps working. A forwarding address is out of scope.

**Daily job.** `runBridgesJob()` is registered as the daily job `bridges` with the one daily-job scheduler (ADR 0016): the in-process scheduler on a long-running server, Vercel Cron through `/api/jobs/daily`. Its outcome is reported per bridge in that run's results. (It first rode on `/api/watches/run`; integration moved it so no second schedule exists.) Notion applies an import without a preview only if the owner switched "import every day" on, and writes back only if write-back is on; Gmail syncs whenever it is connected. Each bridge catches its own errors, so a failure never blocks the watches or the other bridge. A sync is also available on demand (`POST /api/gmail/sync`, and "Import from Notion" in Settings).

**Not verified live.** The Notion REST client and the Google OAuth and Gmail clients were tested against mocked HTTP only: no integration token or Google consent was available where this was built. Notion's schema was read through the owner's connected Notion tools (read-only), which is how the defaults were chosen; the REST request and response shapes follow Notion's and Google's public documentation.

Rejected: the Notion SDK or a Google client library (a few endpoints; no new dependency to trust with a token); storing the Notion token or Google client secret in the document store (they belong to the deployment, not the data); storing message bodies, or a cache of them, to re-parse later (nothing to leak; the parser is deterministic and the message is still in Gmail); a broader Gmail scope such as `gmail.modify` or labels (read-only is all it needs); a Google Pub/Sub watch (a public endpoint and a renewal job for a daily need); fuzzy city matching for Notion labels (a wrong window on the wrong city is worse than one question); deriving windows from the "Best / Avoid" prose (two sources for one fact, and prose is not a schema); applying an import with no preview as the default; an LLM in the mail path (cost, a second place where mail content leaves the server, and the stored prompt already covers that for those who want it).
