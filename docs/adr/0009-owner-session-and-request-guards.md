# The owner signs in to a cookie session; every paid or personal route is guarded

Supersedes the "token in the browser" half of ADR 0004 and ruling R2 ("`/api/bookings` stays ungated").

Three things were open. `/api/bookings` held passenger names, birth dates, emails and phone numbers behind no gate at all. `/api/agent/*` and the shortlist were open and unlimited, so anyone with the URL could spend the owner's Anthropic key or edit the saved places. And the browser authenticated by keeping `MERIDIAN_TOKEN` itself in `localStorage`, where any script on the page could read it, forever.

**Sign-in.** `POST /api/auth/login` takes the password (still `MERIDIAN_TOKEN`, so nothing has to be reconfigured) and sets a session cookie: `HttpOnly`, `SameSite=Lax`, host-only, 30 days (`SESSION_TTL_DAYS`), and in production `Secure` under the `__Host-` name. The cookie value is `v1.<payload>.<HMAC-SHA256>`, where the payload is `{ uid, sid, iat, exp }`. `uid` is always `"owner"`; it is there so more users can follow without a new format. The signing key comes from `SESSION_SECRET`, or, when that is unset, is derived from `MERIDIAN_TOKEN` by HMAC under a fixed label, so the cookie never contains the password and changing the password ends every session. A session past half its life is re-issued on use. `POST /api/auth/logout` clears the cookie and records the session id as revoked in the document store (`auth.json`), so a copied cookie stops working too; other server instances learn of it within 30 seconds. `GET /api/auth/session` says whether the browser is signed in. The browser now stores one flag, `meridian.session = "1"`, so a reload paints the signed-in screens at once; the old `meridian.token` entry is deleted on first load, after being used once to sign in.

**Lockout.** Five wrong passwords from one client in 15 minutes lock that client out for 15 minutes; thirty from all clients together pause password sign-in for everyone for 15 minutes. Both answer 429 with `Retry-After`. Counts live in the document store under a keyed hash of the address, so they survive restarts and are shared across serverless instances when Postgres is the backend. If the store cannot be reached, the same logic runs in memory.

**Automation keeps the Bearer token.** `Authorization: Bearer $MERIDIAN_TOKEN` still opens every gated route, for the import task and cron. `CRON_SECRET` may now differ from the token: it is accepted for `GET /api/watches/run` only. A request that presents an `Authorization` header is judged on it alone, and twenty wrong ones from a client in 15 minutes get 429. That state-changing `GET` refuses the cookie, because a link from another site would carry it.

**CSRF and CORS.** Because the browser now attaches the credential by itself, every state-changing `/api/*` request must carry an `Origin` that is this site (its host equals the `Host` header), one listed in `MERIDIAN_ALLOWED_ORIGINS`, or, outside production, any port on `localhost` (the Vite dev server). Requests with an `Authorization` header are exempt; a request with the cookie but no `Origin` is refused. CORS answers only those same origins, with credentials, never `*`.

**Gates.** All of `/api/bookings` needs the owner, except `POST /search`, which holds no personal data: it is open while it returns mock offers and owner-only once `DUFFEL_API_KEY` or `SERPAPI_KEY` is set. `/api/agent/*` follows the same rule on `ANTHROPIC_API_KEY`: the keyless mock stays open, the keyed path needs the owner (`GET /models` makes no model call and stays open). Shortlist reads stay public; writes need the owner. In the app, the Flights screen, the booking sheet and Ask show the existing unlock card where they are locked.

**Rate limits.** An in-process limiter counts per client address, with a cap across all clients so rotating addresses cannot run up a bill: the agent 20 a minute (600 an hour overall), flight search 20 a minute (600), the news briefing and place news 30 a minute (900), and seasonality fetched on demand from Open-Meteo 30 fetches a minute (600), counted per fetch so cached reads are free. Over the limit is 429 with `Retry-After`. The client address is the socket's unless a proxy is declared: Vercel's own headers are trusted on Vercel, and `TRUST_PROXY=<hops>` picks the entry that many from the right of `X-Forwarded-For`.

**Headers.** Every response carries a Content-Security-Policy (scripts from this site only; styles from this site, inline attributes and Google Fonts; fonts from this site and `fonts.gstatic.com`; images from this site and Wikimedia; connections to the API and the Natural Earth outlines host; `blob:` workers for MapLibre; `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and HSTS in production. One function builds them; the Hono app sends them for everything it serves, and the Vercel build writes the same set onto the static routes. The theme bootstrap moved from an inline script to `/theme-init.js` so the policy needs no `'unsafe-inline'` for scripts.

Consequences. On serverless, rate-limit counters are per warm instance and reset on a cold start, so the limits there are a brake, not a budget; the login lockout does not have this weakness when Postgres is configured. Behind a proxy that is not declared with `TRUST_PROXY`, all clients share one bucket, which is stricter and never looser. The API and the frontend must be the same site for the cookie to be sent; a frontend on another origin needs `MERIDIAN_ALLOWED_ORIGINS` and the same registrable domain. A local run without `MERIDIAN_TOKEN` can still search mock flights and use the mock Ask, but cannot list or make bookings.

Rejected: a hosted auth provider or OAuth (one owner, one password, no third party to trust with it); keeping the bearer token in `localStorage` (readable by any script, never expires); server-side session rows instead of a signed cookie (a store read on every request for no gain with one user; revocation is the only state kept); a double-submit CSRF token (the Origin check needs no client code and covers every route, including ones added later); Redis or a store-backed rate limiter (another service to run for a personal app; the in-process limiter is honest about its serverless limit); and gating flight search and the mock Ask unconditionally (it would break the keyless local run for no data protected).
