# The journal is server-side and token-gated; a Journey is distinct from a Trip

The browser token and "bookings stay ungated" parts are superseded by ADR 0009.

Journeys are durable personal history that ingestion jobs write from outside the browser, so they live server-side in `data/journal.json` (atomic write), not localStorage. Every new route (`/api/journal*`, `/api/replay*`, `/api/watches*`, `/api/import*`) requires `Authorization: Bearer $MERIDIAN_TOKEN`. The gate fails closed: if the token is unset, gated routes return 401 `{error: "journal_locked", reason: "token_not_configured"}`, and the comparison is constant-time. The browser keeps the token the user pastes once (`meridian.token`). Bookings stay ungated in this build (R2): `/api/bookings*` already holds passenger PII unauthenticated, and gating it breaks clients that send no header, so it waits on tension T1. A Journey is something that happened; a Trip is a client-side plan (ADR 0001 unchanged). A Journey can be promoted from a Trip plus its Bookings, and a Trip can be repeated from a Journey, but neither owns the other. Rejected: localStorage for journeys (ingestion cannot write it, and it is per-browser), reusing Trip as the record of past travel (it forces the Trip-to-server migration ADR 0001 rejected), and rate limiting alone on the public instance (it still exposes travel history to anyone who finds the URL).
